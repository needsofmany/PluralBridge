### Scope without a graph walk

The trigger does not discover accounts. It writes the keys that are on the changed row, including the deleted image and the inserted image.

- The row has `AccountId`. Bump that account’s graph or display revision, including when the new object id is not in any snapshot. This covers a new placement, a new legacy root, a new access grant, and removal of any of those.
- The row has no `AccountId`. Bump a revision for each old and new endpoint key: parent and child, system and group, place and member. A context is stale when it contains any of those keys. An added child is noticed because the parent key moves, not because the new child was already stored. An account whose context contains neither endpoint does not show that object today. Its next opening load reads the database directly.
- The row is `pb_system_membership_statuses`, or the trigger cannot name an account or an endpoint. Bump one global graph revision. Every retained context stores that value and becomes stale. This is the conservative case, used for a lookup change that rewrites the meaning of many memberships.
- A navigation-display column on the same row bumps the display revision for that same account, endpoint, or global scope. It does not bump the graph revision.

A context built for account A stores four kinds of values: A’s graph revision, A’s display revision, the global graph and display revisions, and the graph and display revisions of each object id it contains. The next request treats the context as stale for connectivity when any stored graph revision differs. It treats navigation as stale when any stored display revision differs. A difference is enough. The numbers are not an order of commits.

New reachability that this covers:

- New grant or new root with `AccountId`: the account revision moves even though the new id is absent from the snapshot.
- Addition under a parent the account already reaches: the parent endpoint revision moves.
- Removal: the deleted endpoint and the account id, when present, both move.
- Relationship change: every old and new system id moves. A context that holds any of them is stale.
- Change that only creates an object nobody’s context contains, and that has no `AccountId`: no current context can display it. The next opening load sees it. No broadcast.

## Proposals requiring revision

The notes below preserve the earlier design discussion. They are not approved. The items that put revision-counter updates, dependency lookups, or domain-specific recovery on a trigger or on queue management require revision against the messaging boundaries.

1. Trigger publication and deferred cleanup. The draft had the trigger collect revision keys and publish those revisions in the writer's transaction, then insert queue rows, while a processor only deleted old queue rows. Alternatives were a queue-only trigger with the processor publishing revisions, or revisions with no queue. The tradeoff was lock time against a gap while a processor is down. This assigns domain publication and recovery shape to the trigger and the processor. It requires revision. Retention length, column names, and whether write-authorization changes are notified while saves stay on the live write query remain open.

2. Where a revision becomes visible. The draft preferred counters updated in the writer's transaction over waiting for a processor. It also said a queue identity is not commit order. Both the direct update and the queued update are mechanisms. Neither is approved. Overlapping writers and a crashed processor are still open problems, not solved by the messaging boundaries.

3. Opening-build isolation. The draft used one SNAPSHOT transaction to read counters, build the graph, and read access facts, with later requests reading current counters under the database default. The alternative was one statement at a time under read committed snapshot. Two reads inside one snapshot do not prove that nobody committed during the build. This construction is not approved. A time backstop beside any later check is open.

4. A request already running after revocation. The draft treated the counter compare, plus the account binding, as the point where a request may use the retained context, and allowed that request to finish if revocation committed afterward. Cancelling the in-flight response was the alternative. This policy is not approved. How long a context id lives, and which session may hold it, are open.

5. What survives cleanup. The draft kept revision rows, allowed queue history to be deleted, and required a full opening build when a reader still needed a deleted history row. Keeping history forever, or deleting the revision rows, were the alternatives. This is not approved. Who deletes history, and how a cleanup crash is retried, are open.

6. Labels for targets outside the displayed graph. The draft had the trigger seek pb_anchor_relationships on the target index and update display revisions for each source. A global display revision, or the same seek in a processor or a reader, were the alternatives. The target index can support that seek. Placing the seek and the revision update in the trigger, or placing domain recovery in queue management, requires revision. Whether a label change reruns the opening build or patches labels is open.

7. Visibility lookup. The draft had a visibility-type change update one global member revision and one global placement-setting revision, without a graph revision. The alternative was a fan-out across pb_members and both permission tables. The profile dependency on VisibilityCode and DisplayName is confirmed. Which component publishes the notification, and whether the response is global or per row, is open.

A proposed stored shape, also not approved, was one account revision row, one object revision row, one global revision row, one content revision row, and an append-only queue row per changed source key. A sequence on that queue would not be commit order.

TRUNCATE and bulk load without FIRE_TRIGGERS still bypass a database trigger. What happens after those statements is unresolved.
