### Scope without a graph walk

The trigger does not discover accounts. It writes the keys that are on the changed row, including the deleted image and the inserted image.

- The row has `AccountId`. Bump that account’s graph or display revision, including when the new object id is not in any snapshot. This covers a new placement, a new legacy root, a new access grant, and removal of any of those.
- The row has no `AccountId`. Bump a revision for each old and new endpoint key: parent and child, system and group, place and member. A context is stale when it contains any of those keys. An added child is noticed because the parent key moves, not because the new child was already stored. An account whose context contains neither endpoint does not show that object today. Its next opening load reads the database directly.
- The row is `pb_system_membership_statuses`, or the trigger cannot name an account or an endpoint. Bump one global graph revision. Every retained context stores that value and becomes stale. This is the conservative case, used for a lookup change that rewrites the meaning of many memberships.
- A navigation-display column on the same row bumps the display revision for that same account, endpoint, or global scope. It does not bump the graph revision.

A context built for account A stores four kinds of values: A’s graph revision, A’s display revision, the global graph and display revisions, and the graph and display revisions of each object id it contains. The next request treats the context as stale for connectivity when any stored graph revision differs. It treats navigation as stale when any stored display revision differs. A difference is enough. The numbers are not an order of commits.

New reachability that this covers:

- New grant or new root with `AccountId`: the account revision moves even though the new id is absent from the snapshot.
- Addition under a parent the account already reaches: the parent endpoint revision moves.
- Removal: the deleted endpoint and the account id, when present, both move.
- Relationship change: every old and new system id moves. A context that holds any of them is stale.
- Change that only creates an object nobody’s context contains, and that has no `AccountId`: no current context can display it. The next opening load sees it. No broadcast.

The governing requirements, by section:

1. Authority and scope. The pattern is transport-independent. A database, an in-memory queue, or another transport may implement it. Subscriber internals are black boxes and are outside this task. Storage, synchronization, transport, and recovery mechanisms remain subject to review.

2. Separation of responsibilities. The publisher creates a typed message, supplies its identity, subject or key, payload, and TTL, and sends it through the publication interface. Publication stays small. The queue infrastructure owns delivery tracking, reference-counted outstanding-work accounting, expiration enforcement, and queue health. It publishes generic results and lifecycle notifications. It does not take task-specific processing or recovery decisions. The subscriber reports completion and the result through messages, does not directly modify shared reference counts or dirty state, and decides whether to publish replacement work as a new message with its own identity and TTL.

3. Message lifetime. Every message has a publisher-chosen TTL. That includes domain notifications, completion reports, result messages, error notifications, poison notifications, and other lifecycle messages. TTL begins when the publisher sends the message. The generic TTL start is that send. It is not undecided. Every transport must define its precise send boundary and clock semantics. Those details remain open. The generic pattern does not mandate a database insert, a commit, subscriber activation, or a processing-start boundary. The lifetime is immutable. Delivery, processing, persistence, recovery, and restart do not reset, pause, or extend it. A replacement is a new message with a newly chosen TTL. It does not revive or extend the original.

4. Reference-counted dirty state. Infrastructure owns outstanding obligations and dirty state for a defined message or task scope. Accepted work registers its obligations. An accepted completion report discharges only its identified obligation, exactly once. The scope remains dirty while obligations remain. Completion of older work must not erase newer obligations. Workers report through messages and never directly modify that shared accounting. The physical representation, including a counter, a bitset, or records, remains open.

5. Two terminal outcomes. Completed means the registered outstanding obligations were accounted for before TTL expiration. Infrastructure closes the message and publishes its result. Poisoned means TTL expires before the message completes. Infrastructure retires the message, closes its remaining bookkeeping obligations, and publishes the poison outcome. Exactly one terminal outcome applies. Expired means the TTL has elapsed. Expiration before completion produces Poisoned. Stalled means unfinished work and may produce a health notification. It is not a third terminal state. Poison cleanup must not manufacture a Completed outcome because the cleanup reduced outstanding accounting to zero. An accepted completion report may carry an error result and still discharge its identified obligation. Publishing Error or StillDirty alone does not discharge an obligation of the original work. An error does not, by itself, create a third terminal message state.

6. Completed does not mean successful. Completed is lifecycle accounting. The published result carries success, error, or another defined result. A message may complete with an error result. Zero outstanding obligations is accounting completion for that scope only. The database remains authoritative for workspace data changes. Subscriber contracts govern application-specific freshness. Those statements are compatible with accounting completion. Messaging accounting does not solve database freshness.

7. Completion and concurrency. Infrastructure accounting tolerates out-of-order completion reports. A task may separately require processing or result ordering. No workspace-specific ordering contract is selected. Every completion identifies the work it reports. An accepted completion report discharges only that obligation, exactly once. A duplicate, late, expired, unknown, or obsolete completion must not double-discharge accounting, close another obligation, or revive a terminal message. Every completion report has its own TTL and must be valid when accepted. The atomic transition and the exact deadline boundary remain open. Publishing Error or StillDirty alone does not discharge an obligation belonging to the original work. StillDirty does not authorize infrastructure to construct a domain-specific replacement. The matching subscriber decides whether to publish replacement work with a new identity and TTL. Every resulting message follows the same TTL rules. No message is exempt from TTL.

A single call cannot observe an expired report, because elapsed time at the send instant is zero.
